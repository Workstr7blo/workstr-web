# NWC workout-program zaps

Maintainer guide for configuring, testing, and troubleshooting the Nostr Wallet Connect (NWC/NIP-47) zap flow used to pay workout-program creators from Workstr.

This document covers the program-creator zap path. The same wallet connection is also used by the Support Workstr zap path, but creator zaps add program-recipient resolution, a program-address tag, local attempt status, and missing-recipient handling.

## Runtime configuration

There are no required build-time or server-side environment variables for the browser PWA NWC workout-zap flow.

The connection is configured by the user at runtime:

1. The user creates a Nostr Wallet Connect connection string in a wallet that supports NIP-47.
2. The user pastes that `nostr+walletconnect://...` URI into Settings -> Zap wallet (NWC).
3. Workstr validates the wallet by sending a `get_info` request through the relay(s) embedded in the URI.
4. Workstr only saves the connection if the wallet advertises `pay_invoice`.
5. The active connection is saved device-locally in the dedicated NWC secure-storage repository, not in normal settings, encrypted sync records, JSON exports, localStorage, logs, or UI text.

Required URI fields:

- Wallet service pubkey in the URI authority/path: a 64-character hex pubkey.
- `relay=` query parameter: one or more `ws://` or `wss://` wallet relay URLs. These are the only relays used for NWC requests.
- `secret=` query parameter: a 64-character hex client secret generated by the wallet connection flow.

Optional URI fields:

- `lud16=` display label for the wallet.
- `expires_at=`, `expiry=`, or `expires=` Unix timestamp. Expired URIs are rejected before validation.

Security and maintainer caveats:

- Treat the full NWC URI as a spending credential. Anyone with the `secret` can request invoice payment within the wallet's budget and permission policy.
- Never commit, paste into issue comments, log, or include a real NWC URI in test fixtures.
- Use a wallet-side budget limit and very small test amounts for manual validation.
- Workstr masks display as `nostr+walletconnect://<pubkey-prefix>…?relay=<relay-host>` and redacts `secret`, `token`, private keys, raw 64-hex secrets, and `nsec`-like values from errors.

## Connecting a real wallet

1. Open a wallet that supports Nostr Wallet Connect / NIP-47.
2. Create a new connection for Workstr with `pay_invoice` allowed.
3. Set a low spending budget and, when supported by the wallet, a short expiry while testing.
4. Copy the NWC URI.
5. In Workstr, open Settings -> Zap wallet (NWC) -> Connect wallet.
6. Paste the URI and submit.
7. Confirm the UI shows the wallet label or masked connection and the wallet relay host.

Expected validation behavior:

- Malformed URI, non-NWC URI, Lightning address pasted by mistake, missing pubkey, missing secret, bad secret, no relay, non-websocket relay, and expired URI fail immediately.
- Unreachable relay, wallet timeout, unsupported `pay_invoice`, unauthorized/rejected wallet response, or unknown wallet response fail without saving the credential.
- Validation performs `get_info`; a connected wallet must advertise `pay_invoice`.

## Mocking an NWC wallet

Automated tests should not depend on a funded wallet, live wallet credentials, or a third-party LNURL-pay service.

Use one of these approaches:

1. Unit-level mock transport: pass a custom `NwcClientTransport` through the `nwc` option in `verifyNwcConnection`, `validateNwcConnection`, `payInvoice`, `executeSupportZap`, or `executeWorkoutProgramZap`. Existing tests use this to assert exact NWC payloads and error mapping without opening sockets.
2. Stubbed invoice fetcher: pass `fetchInvoice` to `executeWorkoutProgramZap` or `executeWorkoutProgramZapWithStatus`. This isolates NIP-57 request creation and NWC payment from external LNURL services.
3. Local integration harness: run `tests/nwc-mock-wallet-integration.test.ts`. It starts a local WebSocket relay acting as a NIP-47 wallet, uses deterministic non-secret fixture keys, starts a local LNURL-pay HTTP endpoint, validates `get_info`, returns a 21-sat invoice, and can simulate `PAYMENT_FAILED`.

Run the local harness with:

```bash
npm test -- --run tests/nwc-mock-wallet-integration.test.ts
```

Do not reuse the deterministic mock-wallet keys outside the test harness. They are public fixtures, not wallet credentials.

## High-level zap flow

A successful workout-program creator zap performs these steps:

1. User opens a published program card and chooses `Zap creator`.
2. UI requires an active NWC wallet. If none is active, it routes the user to connect one first.
3. `executeWorkoutProgramZapWithStatus()` writes a pending local attempt so the UI can show in-flight state and recover state after navigation.
4. `resolveWorkoutProgramZapRecipient()` validates the program can receive a zap:
   - Program must be a published Nostr workout program, not a purely local draft.
   - Address must be a NIP-101e kind `33402:<author-pubkey>:<d-tag>` address.
   - Author pubkey must be 64-hex and must match the address author.
   - Author metadata must expose `lud16`, `lud06`, or explicit zap-recipient LNURL metadata.
   - Recipient relays must be `ws://` or `wss://` URLs.
5. `buildWorkoutProgramZapRequestPayload()` creates an unsigned NIP-57 kind `9734` zap request with:
   - `relays` tag for zap receipt discovery.
   - `amount` tag in millisats.
   - `p` tag for the program author.
   - `a` tag for the workout program address.
   - `lnurl` tag for the recipient LNURL.
   - `client` tag set to `workstr`.
   - `app` tag set to `workstr`.
   - Comment as event content, after trimming and validation.
6. The user's Workstr identity signer signs the kind `9734` zap request. The NWC client secret is not used as the identity signer.
7. Workstr fetches the recipient LNURL-pay metadata and requests an invoice from the callback with `amount=<millisats>` and `nostr=<serialized zap request>`; comment is included when present.
8. `buildNwcZapPaymentPayload()` checks the returned BOLT11 invoice parses and matches the requested sat amount.
9. `payInvoice()` sends a NIP-47 `pay_invoice` request to the wallet relay(s), encrypted with NIP-04 to the wallet pubkey and signed by the NWC client secret.
10. On successful wallet response, Workstr records a succeeded attempt with safe metadata such as amount, program address, recipient pubkey/LNURL, invoice, payment hash, and fees paid. It does not persist the preimage in attempt status.

## Missing recipient behavior

Missing or invalid recipient information should fail before invoice fetching or wallet payment.

Expected structured recipient failures include:

- `unsupported-program` — local draft or unsupported program shape.
- `missing-pubkey` — no program author pubkey.
- `malformed-pubkey` — author pubkey is not valid 64-hex.
- `missing-lnurl` — no `lud16`, `lud06`, or zap-recipient LNURL metadata.
- `malformed-lnurl` — zap metadata is neither a valid Lightning address nor a valid `lnurl1...` value.
- `malformed-relay` — recipient relay metadata is not websocket-based.
- `malformed-address` — program address is not kind `33402`, has no `d` tag, or does not match the recipient pubkey.

The public creator-zap result maps these to `invalid-recipient` with nested `recipientError`. Tests assert that missing LNURL metadata does not call the LNURL callback and does not send `pay_invoice`.

Troubleshooting recipient failures:

- Confirm the program has been published and has a `33402:<pubkey>:<d>` address. Local-only programs cannot be zapped until published.
- Confirm the program author pubkey is present and matches the address author.
- Query or inspect the author's kind:0 metadata for `lud16` or `lud06`.
- If `lud16` is present, verify it maps to `https://<domain>/.well-known/lnurlp/<name>`.
- If `lud06` is present, verify it decodes to an HTTP(S) LNURL-pay endpoint.
- Confirm any explicit recipient relay URLs are `ws://` or `wss://`.

## Payment failure behavior

Payment and invoice failures are expected to be non-throwing, structured results that the UI/status layer can show safely.

Common failure classes:

- `missing-wallet-connection` — no active NWC wallet was available.
- `invalid-zap-request` — amount/comment/relay/payload validation failed before signing.
- `signing-failed` — identity signer failed, was unavailable, or the user rejected signing. User rejection maps to a cancelled attempt in status persistence.
- `invoice-request-failed` — LNURL metadata or callback request failed, target does not support Nostr zaps, target min/max rejects the amount, or no invoice was returned.
- `invalid-invoice` — invoice is missing, cannot be parsed, or amount does not match the requested zap amount. Workstr must not ask the wallet to pay an amount-mismatched invoice.
- `payment-failed` — wallet rejected or failed `pay_invoice`, timed out, returned no preimage, or returned another NWC failure.

NWC wallet errors are normalized in `src/nostr/nwc-client.ts`:

- `NOT_IMPLEMENTED` -> unsupported method / rejected unauthorized.
- `UNAUTHORIZED`, `FORBIDDEN`, `RESTRICTED` -> rejected unauthorized.
- `EXPIRED`, `EXPIRED_CONNECTION` -> expired connection.
- `INVALID_REQUEST` -> invalid request.
- `PAYMENT_FAILED`, `INSUFFICIENT_BALANCE`, `QUOTA_EXCEEDED` -> payment failure.
- `RATE_LIMITED`, `TEMPORARY_ERROR`, `INTERNAL`, `OTHER`, malformed or unverifiable replies -> unknown failure.
- Client-side wallet timeout maps to the unreachable-service kind.

Troubleshooting payment failures:

- Check the wallet app first; a payment may be pending, rejected, budget-limited, expired, or already paid even if the browser lost the reply.
- Verify the NWC connection is still active and has not expired.
- Verify the wallet budget allows the requested amount and fees.
- Verify the wallet supports `pay_invoice` and the connection was not created read-only.
- Verify wallet relay reachability from the browser/network where Workstr is running.
- Verify the LNURL provider returns `allowsNostr: true`, accepts the amount, and returns a BOLT11 invoice for the same amount.
- Do not retry large payments blindly after a timeout; inspect wallet history first.

## Manual validation: successful creator zap

Use this when validating against a real wallet or a wallet's test/sandbox mode.

Prerequisites:

- A low-budget NWC connection with `pay_invoice` permission.
- A signed-in Workstr identity signer. This is the key that signs the NIP-57 zap request; it is separate from the NWC client secret.
- A published workout program with a valid kind `33402` address.
- The program author's kind:0 metadata has a working `lud16` or `lud06` zap target that supports Nostr zaps.
- A tiny test amount that is inside the LNURL target min/max range and inside the wallet budget.

Steps:

1. Start Workstr locally:

   ```bash
   npm run dev
   ```

2. Open the local Vite URL in a browser profile that has no production wallet secrets unless you intentionally use them for this test.
3. Sign in with the intended Workstr identity signer.
4. Open Settings -> Zap wallet (NWC), paste the low-budget NWC URI, and validate/save.
5. Open or import a published program whose author has `lud16`/`lud06` metadata.
6. Expand the program card and click `Zap creator`.
7. Enter a tiny amount and optional note.
8. Confirm the signer prompt for the kind `9734` zap request.
9. Confirm or observe the wallet payment approval, depending on the wallet's policy.
10. Verify Workstr shows the creator-zap attempt as succeeded with the amount.
11. Independently verify the wallet history shows the same payment.
12. If receipt visibility matters for the scenario, query the author's zap receipts on the advertised relays and confirm a kind `9735` receipt appears with matching `p`, `a`, `amount`, and `description`/BOLT11 data.

Stop and investigate instead of claiming success if:

- The wallet app shows pending/unknown status.
- Workstr timed out but the wallet may still have paid.
- The invoice amount does not match the requested amount.
- The author metadata lacks a zap target.
- The program is local-only or its address does not match the author pubkey.

## Known limitations

- The Kanban verification environment did not contain real funded NWC credentials. Manual QA used a deterministic local mock NIP-47 wallet relay and local LNURL-pay endpoint.
- No real external LNURL-pay provider was called during automated or mock-wallet validation.
- Browser live smoke in the headless Kanban environment could not launch Chrome; local preview returned HTTP 200 and UI behavior is covered by jsdom tests.
- Automated tests prove Workstr's payload building, storage boundaries, protocol calls, invoice checks, and error mapping. They do not prove that every third-party wallet app accepts the same permission prompt, timeout behavior, or approval UX.
- A successful `pay_invoice` response is not the same as verified public receipt indexing. If a feature depends on public receipt display, also verify the resulting kind `9735` receipt from the recipient's LNURL provider/relays.
